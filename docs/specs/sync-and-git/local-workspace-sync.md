# Local workspace sync

> Domain: [sync-and-git](../README.md) · Status: Implemented · Source: rationalized from openspec specs (2026-08-28)

## Purpose

Defines the mirror sync: the local/remote worktree binding, the safe
bootstrap of both sides, the persisted baseline with three-way
reconciliation, and continuous bidirectional synchronization over the
tunnel's `fs` channel. The mirror is the tool for live interactive editing
(1 user : 1 session); autonomous parallel work SHALL use the
[git-native workflow](git-native-workflow.md) instead.

## Scope

In scope:
- `--sync <dir>` binding on `run`, `shell` and `task`, its persistence and reuse.
- Bootstrap classification and initialization policies (`abort`, `local-wins`, `remote-wins`, `union`).
- Persisted baseline and three-way reconciliation (adds, modifications, deletions, convergence, conflicts).
- Application-level convergence barrier before the workload starts.
- Continuous live sync during interactive sessions and the per-workspace sync lease.
- Ignore rules, per-file size threshold, and Git metadata (`.git`) handling.

Out of scope:
- Git-branch-based autonomous sessions ([git-native workflow](git-native-workflow.md)).
- The tunnel transport primitives themselves (`tunnel/transport.js`, `tunnel/sync.js`).
- Storage backends and checkpointing.

## Requirements

### Binding

- **R1.** The system SHALL allow associating a workspace with an absolute local directory via `--sync <dir>` on the `run`, `shell` and `task` commands; `.` SHALL be resolved to the canonical current directory.
- **R2.** The binding SHALL be persisted only in the local machine's configuration, separately from the workspace's central identity, and reused on subsequent invocations on the same machine. `--no-sync` SHALL disable the binding for the single invocation without deleting it.
- **R3.** A persisted binding whose path is absent or inaccessible MUST produce an error before any local or remote mutation, indicating how to rebind with `--sync` or proceed with `--no-sync`.
- **R4.** The system MUST NOT import or interpret binding paths from the central registry: a workspace opened from a machine with no local binding proceeds with the existing remote behavior until the operator specifies `--sync`.

### Bootstrap

- **R5.** Before the first sync, the system SHALL classify local and remote as semantically empty or non-empty, ignoring only the metadata generated by the SCH bootstrap (including the empty Git repository created by `init-workspace.sh`).
- **R6.** If only one side is non-empty, that side SHALL automatically initialize the empty side. If both are non-empty and identical, a baseline SHALL be established without destructive transfers.
- **R7.** If both sides are non-empty and diverge without a baseline, the `abort` default MUST terminate without writing or deleting files, reporting the conflicting paths and the available explicit policies. The operator MAY explicitly select `local-wins`, `remote-wins` or `union` for that invocation.
- **R8.** `local-wins` and `remote-wins` SHALL make the losing side equivalent to the authoritative side for syncable paths, including removals. `union` SHALL preserve paths present on only one side and MUST stop without overwriting when the same path has different contents on the two sides.
- **R9.** Potentially destructive bootstrap policies MUST NOT be persisted in the binding.

### Baseline and three-way reconciliation

- **R10.** After a completed bootstrap or synchronization, the system SHALL atomically persist a local baseline per workspace and binding containing the format version, the workspace identity, the fingerprint of the local root, and the per-file state of the last convergent point.
- **R11.** On subsequent openings the system SHALL compare baseline, local and remote: a change present on only one side is propagated to the other; identical changes on both sides converge without conflict; a deletion on only one side is propagated; different changes to the same path on the two sides are a true conflict.
- **R12.** A baseline that is invalid, belongs to another binding, or is incompatible MUST NOT be used to authorize deletions and SHALL send the flow back to the safe bootstrap rules.

### Conflict policies

- **R13.** For a true conflict, the system SHALL apply the policy of the single invocation: `abort` (default) does not modify the path; `local-wins` propagates the local copy; `remote-wins` propagates the remote copy; `keep-both` keeps the remote copy under the original name and materializes the local copy with a deterministic conflict suffix that does not overwrite existing files.
- **R14.** Every conflict MUST be reported on stderr with path, decision, and preserved side. No conflict policy other than `abort` SHALL be persisted implicitly.

### Convergence barrier

- **R15.** The sync protocol SHALL provide an application-level barrier confirming that all transfers planned before the barrier have been received, applied atomically, and observed by both sides. `ready` MUST NOT be declared until the preflight's pulls, pushes, deletions and conflict decisions have passed that barrier.
- **R16.** The baseline SHALL be replaced only after the barrier. An error or disconnection before the confirmation SHALL leave the previous baseline intact and MUST prevent the workload from starting.

### Continuous sync and lease

- **R17.** During a synchronized interactive session, the system SHALL maintain a dedicated `fs` channel alongside the CommandShell channel and propagate creations, modifications and deletions in near-real-time in both directions against the active backend's worktree, with atomic application and reliable reconnection.
- **R18.** The runtime MUST grant at most one sync lease per workspace: a second `run`, `shell` or `acp` session requesting sync SHALL be explicitly rejected without starting a second writer. On client close or detach the lease SHALL be released; the remote workload MAY continue and its changes are reconciled at the next session.
- **R19.** Interactive detach (e.g. `Ctrl+]`) constitutes neither a workload completion barrier nor a guarantee of a final checkpoint.

### Git metadata and exclusions

- **R20.** The system SHALL synchronize worktree files according to an ignore-list and a per-file size threshold that are configurable and consistent on both sides. `.git` MUST be excluded from live sync.
- **R21.** When the authoritative bootstrap side is a Git repository and the opposite side is semantically empty, the system SHALL transfer a consistent initial snapshot of the Git metadata before the barrier. After bootstrap, local or remote Git changes SHALL NOT be propagated as live file events, and the system MUST document and report this limitation when it detects metadata divergence.
- **R22.** A file exceeding the configured threshold SHALL be excluded from the sync plan, with its path, size and reason reported on stderr.

## Behavior

Binding:

```console
$ sch run myws --sync .            # first binding from the current directory
$ sch run myws                     # same machine: binding reused automatically
$ sch run myws --no-sync           # one-shot disable, binding kept
```

- First bind from `/home/me/project` associates `myws` with the canonical path `/home/me/project`.
- A moved/unreadable binding directory fails the command before any sync activity, suggesting `--sync <new-path>` or `--no-sync`.
- The same workspace opened from another machine without a binding does not inherit any path.

Bootstrap:

- Local project + remote-only bootstrap metadata → the project is transferred to the remote with no explicit policy.
- Semantically empty local directory + remote worktree → the local side is hydrated from the remote.
- Both non-empty and divergent without a baseline → `abort` modifies nothing and lists the conflicting paths and policies; `union` with a same-path/different-content collision stops before applying the plan.

Reconciliation (baseline valid):

- Local-only edit since the baseline → transferred to the remote; baseline updated after the barrier.
- Remote-only change (e.g. output of a detached task while the laptop was disconnected) → downloaded at the next sync and recorded in the new baseline.
- File deleted only locally and unchanged remotely → deleted remotely after reconciliation.
- Workspace rebound to a directory with a different fingerprint → the old baseline is ignored for deletion purposes and the no-baseline bootstrap rules apply.
- True conflict with no policy → reconciliation stops before modifying the file; with `keep-both` the remote copy stays at the original path and the local copy is preserved at a unique conflict path on both sides; nothing is lost.

Barrier and lease:

- Local pushes still queued → the TUI/task does not start and the baseline is not updated; on barrier confirmation the new baseline is saved atomically and the workload may start.
- Channel drops before confirmation → the workload does not start, the previous baseline remains valid, and the next invocation repeats a full reconciliation.
- During a session, local saves appear in the remote worktree (e.g. `/home/sch/workspace/repo` on the `s3` backend) and remote harness edits appear locally, both in near-real-time; a second sync client is rejected with a busy-workspace error.

## Invariants

- **I1.** A workspace has at most one active sync lease at any time.
- **I2.** No file is written or deleted on either side before bootstrap classification completes or a policy is explicitly selected.
- **I3.** The persisted baseline always describes the last point at which both sides were observed converged.
- **I4.** A baseline whose root fingerprint does not match the bound directory never authorizes a deletion.
- **I5.** The workload (TUI or task) never starts before the preflight convergence barrier is confirmed.
- **I6.** `.git` is never modified by the live sync watcher after bootstrap.
- **I7.** Destructive bootstrap or conflict policies are never persisted; only `abort` is ever active by default.
