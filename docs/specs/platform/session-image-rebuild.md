# Session image rebuild

> Domain: [Platform](../README.md) · Status: Implemented · Source: rationalized from openspec specs (2026-08-28)

## Purpose

Allow an AgentCore session to delegate the build of the current runtime image to AWS CodeBuild — so an agent that modifies `image/` can produce a new image — without introducing a Docker daemon, rootless builder, or emulation into the microVM.

## Scope

In scope:
- The single in-session rebuild command, source packaging/upload, build start and wait, output tag namespace, separation between built and in-service images, ephemeral build sources.

Out of scope:
- Provisioning of the build project, roles and permissions ([runtime-provisioning](runtime-provisioning.md)).
- Image contents and the rebuild command's presence in the image ([runtime-image](runtime-image.md)).
- Promotion of an image to the runtime (explicit deploy action, outside any session).

## Requirements

**R1.** The system SHALL allow a session to obtain a `linux/arm64` image from the current contents of `image/`, including uncommitted changes, with no Docker daemon, rootless builder, or emulation in the microVM. The build SHALL be managed by AWS and published to the project's ECR repository.

**R2.** The build context SHALL use exclusively the contents of `image/` (Dockerfile and context); no other path of the worktree MAY enter the build.

**R3.** The rebuild command SHALL package the source, upload it, start the build, and wait for its outcome in a single invocation. On success it SHALL exit 0 and print the URI and tag; on failure it SHALL exit non-zero, report the failed phase, and indicate how to consult the logs. While in progress it SHALL report the current phase without requiring log streaming.

**R4.** The image tag SHALL be generated by the build configuration in the infrastructure within the `sessionbuild-*` namespace, never determined by the client: a caller-supplied tag SHALL be ignored. The build configuration MUST NOT reside in the session source. The flow MUST NOT publish to the deployed tag; no produced image may overwrite the tag of the current runtime configuration.

**R5.** Publishing an image from a session MUST NOT modify the runtime, the stack, or active sessions. Promoting an image remains an explicit action external to the session; on success the command SHALL state that the image is not in use and that promotion requires an explicit update that resets the session storage.

**R6.** Build sources SHALL reside under a prefix distinct from the checkpoints (`builds/*`), have configurable retention (set by [runtime-provisioning](runtime-provisioning.md) R14), and use keys that avoid collisions between concurrent sessions: two sessions rebuilding simultaneously SHALL each use their own source, without content from the other worktree.

**R7.** The rebuild command SHALL read the build project and bucket from environment variables injected by the runtime, MUST NOT contain hardcoded AWS identifiers, and SHALL fail immediately (non-zero exit, explicit message, no AWS calls) when that configuration is absent — i.e. when the capability is not enabled.

## Behavior

- A session edits a file under `image/` and runs the rebuild command (available in the image `PATH`, e.g. `sch-build-image`): the source is uploaded under `builds/`, CodeBuild builds `linux/arm64`, and the image is published as `sessionbuild-<timestamp>-<build-number>`.
- Success: exit 0, full image URI printed, plus the "not in use / promotion resets session storage" notice. Failure: non-zero exit, failed phase, log instructions.
- The runtime configuration and version are untouched by any number of rebuilds.

## Invariants

- **I1.** No in-session rebuild ever changes the deployed runtime tag, the stack, or active sessions.
- **I2.** Client-supplied tags never reach the published image; tags always come from the `sessionbuild-*` namespace.
- **I3.** No build engine (Docker daemon, rootless builder, emulator) exists inside the microVM.
- **I4.** Concurrent session builds never share or mix build sources.
